## 二、优化清单

### 2.1 情感分析增强

#### 2.1.1 阴阳怪气检测模型

**问题**：现有SnowNLP无法识别反讽评价（如"好评骗更多人"、"笑死"）

**解决思路**：
1. **数据标注**：人工标注500-1000条阴阳怪气样本，标注规范：
   - 典型阴阳怪气："给个好评骗一下更多的人"、"笑死"、"还行吧（内心不认可）"
   - 真好评：明确的正面表达
   - 真差评：明确的负面表达
2. **模型选择**：微调中文RoBERTa-base做反讽二分类
3. **特征补充**：
   - 评分与情感词矛盾检测
   - 表情符号组合（如👍配负面词）
   - 特定词汇模式（"骗"、"快跑"、"别信"）
4. **集成到现有流程**：在现有情感分析后增加反讽检测分支

**预期效果**：阴阳怪气评价识别准确率 > 85%

---

#### 2.1.2 分层分析策略

**问题**：1000条评论用LLM逐条分析算力/时间成本过高

**解决思路**：
```
┌─────────────────────────────────────┐
│          评论输入 (1000条)           │
└─────────────────┬───────────────────┘
                  ↓
┌─────────────────────────────────────┐
│  第一层：轻量模型快速分类            │
│  (DistilBERT/RoBERTa-base)          │
│  耗时：约2-3分钟                     │
└─────────────────┬───────────────────┘
                  ↓
        ┌─────────┴─────────┐
        ↓                   ↓
   高置信度              低置信度/疑似
   直接输出              阴阳怪气
        ↓                   ↓
        └─────────┬─────────┘
                  ↓
┌─────────────────────────────────────┐
│  第二层：强模型复审（如需要）        │
│  或人工复核                          │
└─────────────────────────────────────┘
```

**优化策略**：
1. 优先分析200条，根据置信度决定是否扩大分析量
2. 批量处理：32-64条/批，充分发挥GPU利用率
3. 结果缓存：相同商品避免重复分析

---

### 2.2 RAG 知识库建设

**问题**：每次分析都是从零开始，未利用历史数据

**解决思路**：
1. **知识库构建**：
   - 收集历史投诉数据、典型差评案例
   - 按品类（手机、家电、美妆等）分类存储
   - 使用中文embedding模型（text2vec-base-chinese）向量化
2. **向量库选择**：Chroma / FAISS / Milvus
3. **检索流程**：
   ```
   新商品评论 → 向量化 → 检索相似历史案例 → 作为分析参考
   ```
4. **LangChain集成**：
   - 使用LangChain的RetrievalQA链
   - 结合LLM生成分析报告时参考历史案例

**技术栈**：LangChain + Chroma + text2vec-base-chinese

---

### 2.3 MCP 架构集成

**问题**：各平台爬虫独立运行，大模型无法直接调用

**解决思路**：
1. **MCP服务封装**：
   ```
   ┌─────────────────────────────────────┐
   │           大模型 (LLM)               │
   └─────────────────┬───────────────────┘
                     ↓
   ┌─────────────────────────────────────┐
   │           MCP Server                │
   │  ┌─────────┐ ┌─────────┐ ┌────────┐ │
   │  │淘宝工具  │ │小红书工具│ │投诉工具 │ │
   │  └─────────┘ └─────────┘ └────────┘ │
   └─────────────────────────────────────┘
   ```
2. **工具定义**：
   - `search_taobao(keyword)` - 搜索淘宝商品
   - `get_comments(item_id, page)` - 获取评论
   - `search_xiaohongshu(keyword)` - 搜索小红书
   - `search_heimao(brand)` - 搜索黑猫投诉
3. **框架**：使用 anthropic/mcp-python-sdk

**价值**：大模型可以自主规划调用工具，完成复杂分析任务

---

### 2.4 模型微调

**问题**：通用模型对商品评论领域适应性不足

**解决思路**：
1. **微调目标**：
   - 商品评论情感分析
   - 阴阳怪气检测
   - 关键词提取
2. **基座模型**：ChatGLM3-6B / Qwen-7B / 中文Llama
3. **微调技术**：LoRA / QLoRA（低显存适配）
4. **训练数据**：
   - 现有标注数据
   - 爬取的商品评论（需清洗标注）
5. **框架**：lora.css / PEFT

**注意**：仅用于推理加速，不建议每条评论都调用LLM

---

### 2.5 Agent 智能体

**问题**：用户需要手动触发各模块，流程繁琐

**解决思路**：
1. **ReAct Agent架构**：
   ```
   用户输入 → 理解意图 → 规划步骤 → 执行工具 → 整合结果 → 输出报告
   ```
2. **工作流程示例**：
   ```
   输入：华为Mate60Pro怎么样
   ↓
   理解：需要分析该商品口碑
   ↓
   规划：
     1. 搜索淘宝商品
     2. 爬取评论
     3. 分析情感
     4. 搜索小红书
     5. 搜索投诉
   ↓
   执行各工具
   ↓
   整合输出报告
   ```
3. **框架**：LangChain Agent / AutoGen

---

### 2.6 品牌+商品搜索功能

**问题**：用户仅有品牌名和商品名，无商品链接

**新增模块**：`product_search.py`

**实现思路**：
1. **淘宝搜索**：
   - 拼接关键词：`品牌名 + 商品名`
   - 爬取搜索结果页面
   - 解析：商品ID、标题、价格、店铺、销量
2. **候选商品选择**：
   - 展示多个候选商品
   - 用户选择或按销量自动取Top1
3. **复用逻辑**：选定商品后调用现有爬虫和分析模块
4. **多平台扩展**：
   - 小红书：搜索品牌+商品相关笔记
   - 黑猫投诉：搜索品牌投诉

**输入格式**：支持空格/逗号分隔，如 "华为 手机"、"小米手环"

---

### 2.7 数据库持久化

**问题**：商品数据未沉淀，无法进行历史对比和推荐

**解决思路**：
1. **数据库选型**：
   - MySQL：商品基础信息、用户数据
   - Redis：缓存、热点数据
   - Elasticsearch：商品搜索
2. **数据表设计**：
   - `products` - 商品基础信息
   - `comments` - 评论数据
   - `analysis_results` - 分析结果
   - `users` - 用户信息
   - `browse_history` - 浏览历史
   - `favorites` - 收藏
3. **定时任务**：
   - 定期更新商品价格、销量
   - 定期重新分析（数据变化时）

### 2.8 Go 后端工程化（新增）

**问题**：当前 Python 服务承担了入口、编排与执行，随着并发增大容易出现阻塞与扩展瓶颈。

**目标**：在不推翻现有 Python 业务逻辑的前提下，引入 Go 作为高并发入口与工程化骨架。

**已完成（负责人：yllmis）**：
1. `go_backend` 框架初始化（`cmd/internal/docs`）
2. API 网关落地：
   - 统一入口与反向代理
   - 健康检查 `/healthz`
   - 请求日志中间件
   - 在途并发限制（超限返回 503）
   - 优雅停机
3. 单元测试覆盖：配置、代理、路由、限流

**下一步（Go侧）**：
1. 增加鉴权中间件（JWT/签名校验）
2. 增加限速/熔断/重试策略
3. 建立任务队列（抓取与分析异步化）
4. 逐步把高频接口从 Python 迁移到 Go（保留算法推理在 Python）
5. 增加监控指标（Prometheus）与链路追踪（OpenTelemetry）

#### 2.8.1 Token 鉴权实现专项（新增整理）

**实现方案**：
1. 采用 Bearer Token（JWT）作为统一鉴权凭证。
2. 基于角色区分权限：`user`、`admin`、`system(worker)`。
3. 中间件链路：日志 -> 鉴权 -> 权限 -> 限流 -> 业务处理。
4. 普通用户仅可查询结果与任务状态，不可直接调用爬虫工具。
5. 查询未命中时由系统创建后台任务并异步调用工具，管理员负责异常兜底与强制刷新。

**预期效果**：
1. 阻断未授权工具调用，降低资源滥用风险。
2. 将高成本任务从同步接口中剥离，提升接口稳定性。
3. 管理员可控重跑，失败任务可审计、可追踪。
4. 为后续用户系统、社区版登录态与配额治理提供统一基础。

## 五、注意事项

1. **爬虫合规性**：当前使用Selenium，存在账号风险，正式版建议使用官方API
2. **数据隐私**：用户搜索历史、收藏等数据需妥善保护
3. **算力成本**：LLM调用需控制成本，优先使用轻量模型
4. **分析准确性**：结果仅供参考，不作为唯一决策依据
5. **测试环境**：建议在测试账号环境下使用爬虫功能
6. **语言边界**：Go负责入口与工程能力（并发、治理、观测），Python继续承载算法推理与数据处理，避免重复建设
