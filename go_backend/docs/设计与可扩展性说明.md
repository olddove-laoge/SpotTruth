# SpotTruth 项目 Go 后端设计与可扩展性说明

## 一、引入 Go 的场景与边界

1. 高并发 API 网关：
   - 作为所有外部请求的统一入口，负责路由、限流、认证、日志、健康检查。
   - 反向代理到现有 Python/Flask 服务，后续可平滑切换部分接口到 Go 实现。
2. 任务调度与异步处理：
   - 对于高并发、IO 密集型或需异步处理的任务（如大批量评论分析、数据抓取），可用 Go 实现任务分发、队列、并发 worker。
3. 领域服务拆分：
   - 随业务增长，将部分高频/高性能需求的 API 拆分为独立 Go 微服务（如用户鉴权、数据聚合、实时统计等）。
4. 工程化与可维护性提升：
   - 利用 Go 的静态类型、部署便捷、跨平台特性，提升后端整体工程质量。

## 二、API 网关设计

- 统一入口，监听 8080 端口。
- 健康检查接口 `/healthz`，便于监控与自动化运维。
- 反向代理所有业务流量到 Flask（127.0.0.1:5000），后续可逐步迁移部分路由到 Go 内部 handler。
- 支持中间件扩展（日志、限流、认证等）。
- 配置全部支持环境变量，便于多环境部署。

### 2.1 已落地能力（当前版本）

1. 高并发连接池：
   - `MAX_IDLE_CONNS`
   - `MAX_IDLE_CONNS_PER_HOST`
   - `IDLE_CONN_TIMEOUT`
   - `RESPONSE_HEADER_TIMEOUT`
2. 并发保护：
   - `MAX_IN_FLIGHT` 控制在途请求上限。
   - 达到上限后快速返回 `503 Service Unavailable`，并返回结构化错误体与 `Retry-After`，保护下游 Flask 服务。
3. 可观测性：
   - 请求日志记录 `method/path/status/duration/remote`。
   - 暴露轻量指标快照接口 `GET /metrics`，用于联调与快速排障。
4. 生命周期管理：
   - 支持 `SIGINT/SIGTERM` 优雅停机。
5. 鉴权组件（库级能力）：
   - 已实现 JWT Token 生成/解析与角色鉴权中间件（`internal/auth`）。
   - 已接入网关主处理链路，默认开启鉴权并提供公共白名单路由。
6. 健康探针分层：
   - `GET /healthz` 用于存活探针。
   - `GET /readyz` 用于上游可用性探针（主动检查 Flask 健康接口）。

## 三、与现有 Python 服务协作

- 保持接口兼容，前端/调用方无感知切换。
- 通过 HTTP/REST 协议通信，必要时可用 gRPC/消息队列做异步解耦。
- 逐步将高并发、性能瓶颈接口迁移到 Go，低频/复杂业务仍由 Python 处理。

## 九、架构进阶与高光扩展方向 (由 Gemini 提出)
设计初衷： 本章节旨在为系统提供更具“分布式系统设计感”的演进路线。考虑到开发周期与交付稳定性，后续扩展将避免底层通信协议的重构（保持 HTTP/REST），而是聚焦于在 Go 网关层引入高级服务治理能力，以极低的改造成本显著提升系统的技术壁垒和工程化水平。

### 9.1 AI Agent 工具并发编排层 (轻量级任务调度)
- 当前现状： 大模型负责意图识别，Go 仅做简单的被动代理或基础的单层批量并发。

- 演进建议： 在 Go 后端抽象出一个轻量级的工作流编排引擎（基于并发设计模式如 Fan-out/Fan-in）。当接收到复杂的组合查询指令（如“同时分析 A、B 两个商品并在小红书和淘宝对比”）时，Go 网关负责将其拆解为有向无环图 (DAG)，并行调用下游 Python 的多个工具（爬虫、情感分析），等待所有 Goroutine 完成后执行结果聚合 (Scatter-Gather 模式)。

- 核心价值： * 完美体现对 Go 并发原语（sync.WaitGroup、Channel、Context 超时控制）的深度掌控。

将“执行面”彻底下沉给 Go，让大模型的 Token 专注在“意图”上，大幅降低响应延迟。

### 9.2 熔断与服务降级机制 (高可用容错设计)
- 当前现状： 已有并发上限保护（快速失败），但对下游 Python 节点因显存 OOM 或反爬虫导致的持续异常，缺乏自动恢复与保护机制。

- 演进建议： 在 Go 网关层引入轻量级断路器模式（如引入开源库 sony/gobreaker）。监控下游 Python Worker 的健康状态。

- 降级策略： 当下游错误率或超时率达到阈值（如 10秒内 50% 请求失败），网关自动触发熔断，拒绝新请求打到 Python 端。熔断期间，网关直接实施“服务降级”——返回兜底的缓存数据或优雅的提示信息（如：“模型算力拥挤，仅返回基础商品信息”），防止微服务雪崩。

- 核心价值： 切中后端高可用架构设计的核心痛点，在比赛演示中能够展示系统极强的稳定性和容灾能力，也是大厂暑期实习面试的绝对高频加分项。

### 9.3 比赛级可视化看板 (Prometheus + Grafana 监控大盘)
- 当前现状： 拥有结构化日志，但仅停留在文本层面，系统运行状态的呈现对评委或外部用户不够直观。

- 演进建议： 开发一个 Prometheus 监控中间件，在 Go 网关暴露 /metrics 接口。核心埋点指标包括：

   - API 吞吐量：网关 QPS 与各类工具的调用频次。

   - 延迟分位数：记录模型推理和爬虫任务的 P99、P95 响应时间。

   - 系统状态：当前的 Goroutine 数量、在途并发请求数、HTTP 状态码（200/4xx/5xx）比例。

   - 部署：配合 Docker 快速拉起一个 Grafana 面板，对接 Prometheus 数据源。

- 核心价值： “一图胜千言”。在比赛答辩 PPT 或现场 Demo 时，一个实时跳动的微服务监控面板能瞬间拉满项目的工业级色彩，是将幕后技术转化为台前亮点的最有效手段。
如需详细设计/接口定义，请在 docs/ 目录补充具体方案。

## 十、Go 后端开源组件使用情况说明

### 10.1 统计口径

1. 本清单仅统计第三方开源组件（即 `go.mod` 中非 Go 官方标准库依赖）。
2. Go 官方标准库（如 `net/http`、`context`、`sync`）属于语言运行时基础能力，不纳入“开源组件使用清单”。
3. 文档同时区分“已落地”与“规划中（未落地）”两类组件，避免与实际代码状态混淆。

### 10.4 是否需要单独列出 Go 官方库

结论：不需要单独作为“开源组件”列出。

原因：

1. 标准库是 Go 语言默认能力，不属于项目自行引入的外部依赖。
2. 对外做技术汇报时，更关注可替换、可升级、需合规审计的第三方组件。
3. 将标准库排除后，依赖边界更清晰，便于后续做许可证盘点和安全治理。

### 10.5 维护建议

1. 每次新增第三方依赖时，同步更新本节与 `go.mod`，保持文档-代码一致。
2. 规划态组件在真正落地前，统一标记为“未引入”，防止误判项目复杂度。
3. 发布前执行一次依赖核对（`go list -m all`），确保说明与产物一致。
