# SpotTruth 项目 Go 后端设计与可扩展性说明

## 一、引入 Go 的场景与边界

1. 高并发 API 网关：
   - 作为所有外部请求的统一入口，负责路由、限流、认证、日志、健康检查。
   - 反向代理到现有 Python/Flask 服务，后续可平滑切换部分接口到 Go 实现。
2. 任务调度与异步处理：
   - 对于高并发、IO 密集型或需异步处理的任务（如大批量评论分析、数据抓取），可用 Go 实现任务分发、队列、并发 worker。
3. 领域服务拆分：
   - 随业务增长，将部分高频/高性能需求的 API 拆分为独立 Go 微服务（如用户鉴权、数据聚合、实时统计等）。
4. 工程化与可维护性提升：
   - 利用 Go 的静态类型、部署便捷、跨平台特性，提升后端整体工程质量。

## 二、API 网关设计

- 统一入口，监听 8080 端口。
- 健康检查接口 `/healthz`，便于监控与自动化运维。
- 反向代理所有业务流量到 Flask（127.0.0.1:5000），后续可逐步迁移部分路由到 Go 内部 handler。
- 支持中间件扩展（日志、限流、认证等）。
- 配置全部支持环境变量，便于多环境部署。

### 2.1 已落地能力（当前版本）

1. 高并发连接池：
   - `MAX_IDLE_CONNS`
   - `MAX_IDLE_CONNS_PER_HOST`
   - `IDLE_CONN_TIMEOUT`
   - `RESPONSE_HEADER_TIMEOUT`
2. 并发保护：
   - `MAX_IN_FLIGHT` 控制在途请求上限。
   - 达到上限后快速返回 `503 Service Unavailable`，保护下游 Flask 服务。
3. 可观测性：
   - 请求日志记录 `method/path/status/duration/remote`。
4. 生命周期管理：
   - 支持 `SIGINT/SIGTERM` 优雅停机。

## 三、与现有 Python 服务协作

- 保持接口兼容，前端/调用方无感知切换。
- 通过 HTTP/REST 协议通信，必要时可用 gRPC/消息队列做异步解耦。
- 逐步将高并发、性能瓶颈接口迁移到 Go，低频/复杂业务仍由 Python 处理。

## 八、代码细扣与待修复清单（2026-03-09）

本节用于沉淀网关代码审查结论，先记录后修复，避免遗漏。

### 8.1 P0（优先修复）

1. 代理层超时保护不完整
   - 位置：`internal/gateway/proxy.go`
   - 现状：当前自定义 `http.Transport` 未显式设置 `DialContext`、`TLSHandshakeTimeout`、`ExpectContinueTimeout` 等关键超时。
   - 风险：上游网络抖动时，可能出现连接长时间挂起，拖垮网关吞吐。
   - 计划：补齐拨号/握手/继续等待超时，并补充慢上游场景测试。

2. 服务端超时策略不完整
   - 位置：`cmd/api-gateway/main.go`
   - 现状：`http.Server` 仅设置 `ReadHeaderTimeout`。
   - 风险：慢请求体、慢响应写入、长连接堆积时保护不足。
   - 计划：补充 `ReadTimeout`、`WriteTimeout`、`IdleTimeout` 配置项与默认值。

### 8.2 P1（下一迭代）

1. 健康检查仅为存活检查
   - 位置：`internal/gateway/server.go`
   - 现状：`/healthz` 固定返回 `ok`，不检查上游可用性。
   - 风险：上游不可用时，网关仍可能被判定为健康。
   - 计划：新增 `readiness` 探针（轻量探测上游），保留 `liveness` 语义。

2. 限流返回语义可增强
   - 位置：`internal/middleware/concurrency_limiter.go`
   - 现状：超限仅返回 `503 service busy`。
   - 风险：调用方缺少重试指引，观测侧缺少命中指标。
   - 计划：增加 `Retry-After`、统一错误体、补充限流命中指标。

### 8.3 跟进方式

1. 每项修复必须配套单测，禁止仅靠手工验证。
2. 每次修复在提交说明中标注对应条目（如 `P0-1`、`P1-2`）。
3. 修复顺序：先 P0，再 P1，避免引入额外不确定性。

## 九、Token 鉴权实现方案与效果（整理版）

本节汇总当前讨论过的 Token 鉴权目标、实现方式、权限边界与预期效果，用于后续开发对齐。

### 9.1 目标与原则

1. 普通用户可发起查询请求，但不可直接操作底层爬虫/重分析工具。
2. 管理员可执行高权限运维动作（强制刷新、重跑任务、参数调优）。
3. 系统任务（Worker）通过受控通道调用工具，保证任务可审计、可限流、可重试。
4. 查询能力与工具能力解耦：用户提需求，系统异步补数。

### 9.2 角色与权限模型（RBAC）

1. 普通用户（user）
   - 允许：查询结果、查看任务状态、管理个人收藏/历史。
   - 禁止：直接调用抓取工具、强制重跑、修改系统参数。
2. 管理员（admin）
   - 允许：强制触发抓取与重分析、重试失败任务、调整执行参数。
   - 约束：所有高权限动作必须记录审计日志。
3. 系统任务（system/worker）
   - 允许：按队列任务调用底层工具，回写结果与状态。
   - 约束：仅可通过服务内网或服务凭证调用，不暴露给前端。

### 9.3 Token 设计

1. Access Token（短期）
   - 建议有效期：15-60 分钟。
   - 携带声明：`sub`（用户ID）、`role`（角色）、`exp`、`iat`、`jti`。
2. Refresh Token（长期，可选）
   - 建议有效期：7-30 天。
   - 用于刷新 Access Token，支持会话续期与失效控制。
3. 签名算法
   - 推荐：`HS256`（单体起步）或 `RS256`（多服务/多环境）。
4. 传输方式
   - HTTP 头：`Authorization: Bearer <token>`。

### 9.4 中间件接入位置

建议链路：`请求日志 -> Token鉴权 -> 权限校验 -> 限流 -> 业务处理/代理`。

1. 鉴权中间件：校验签名、过期时间、基础声明。
2. 权限中间件：按路由匹配角色（user/admin/system）。
3. 失败语义：
   - `401 Unauthorized`：未携带Token、Token无效或过期。
   - `403 Forbidden`：身份有效但无权限。

### 9.5 查询未命中时的异步任务链路

1. 用户查询商品（如“苹果手机评价推荐”）。
2. 先查缓存，再查数据库。
3. 都未命中时：创建后台任务（`jobs`）并投递队列（Redis/MQ）。
4. Worker 异步调用抓取与分析工具，完成后回写结果。
5. 前端显示“请稍候”，轮询任务状态或订阅通知。

说明：普通用户不是直接调用工具，而是触发受控任务。

### 9.6 推荐接口分层

1. 用户接口（对外）
   - `GET /api/v1/search`
   - `GET /api/v1/jobs/{id}`
2. 管理接口（高权限）
   - `POST /api/v1/admin/jobs/rebuild`
   - `POST /api/v1/admin/jobs/retry/{id}`
3. 内部接口（Worker）
   - 仅内网可见，不对前端开放。

### 9.7 安全控制与风控建议

1. 幂等控制：同商品短时间重复请求避免重复建任务。
2. 重试策略：指数退避，最大重试次数后进入人工处理。
3. 审计日志：管理员操作必须落库（操作者、时间、参数、结果）。
4. 黑名单与主动失效：支持注销、封禁后立即失效Token。
5. 密钥管理：生产环境密钥放在 Secret/KMS，不入库不入代码。

### 9.8 预期效果

1. 安全性：阻断未授权工具调用，降低滥用风险。
2. 稳定性：高成本操作统一进入队列，避免接口被重任务拖垮。
3. 成本可控：按角色/配额治理请求，降低无效抓取与重复分析。
4. 可运维：管理员可强制刷新与故障兜底，系统任务自动化执行。
5. 可审计：关键操作可追踪，满足后续运营与合规需求。

### 9.9 落地顺序（建议）

1. 第一步：Access Token + 基础 RBAC（user/admin）。
2. 第二步：任务队列联动权限（用户触发任务，Worker执行）。
3. 第三步：Refresh Token、黑名单、审计看板。
4. 第四步：配合限流/熔断/指标形成完整治理闭环。
