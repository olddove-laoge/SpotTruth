# SpotTruth Go 网关第四阶段实施步骤（D15-D21）

更新时间：2026-04-10
目标范围：方案2（熔断与服务降级）落地 + 基于 `new_idea/run.py` 的联调方案固化

## 一、阶段目标

1. 让 Go 网关具备下游异常时的自动保护能力（熔断、降级、恢复）。
2. 将 `new_idea/run.py` 纳入固定联调链路，验证“Agent 工具调用 + 网关治理”协作行为。
3. 形成可直接复用的故障注入脚本与回归清单。

## 二、联调范围（agent.py 作为底层工具）

联调对象：
1. Agent 层：`new_idea/run.py`（核心实现位于 `new_idea/agent/`）。
2. 工具层：`new_idea/step6_mcp_tools.py`（由 Agent 调用）。
3. 网关层：`go_backend/cmd/api-gateway`。
4. Web 联调层：`web_app/app.py` 对外联调接口。

联调目标链路：
1. Agent 正常分析商品（淘宝评论 -> 反讽识别 -> 情感分析）。
2. 网关健康检查与就绪检查正常返回（`/healthz`、`/readyz`）。
3. 网关在下游异常时提供可解释的失败语义（`GATEWAY_DEGRADED` + request_id + degrade_reason）。

## 五、方案2（Gemini 9.2）实现方案（已落地）

### 5.1 目标能力

1. 熔断触发：连续错误/超时达到阈值后快速拒绝下游调用。
2. 半开探测：冷却后放行少量探测请求，决定恢复或继续熔断。
3. 服务降级：熔断打开时返回统一降级响应，避免调用方长时间等待。

### 5.2 技术方案（已落地）

1. 依赖引入
   - 已引入 `github.com/sony/gobreaker` 并接入网关链路。

2. 网关改造点
   - 在上游调用封装层接入断路器执行器。
   - 对 5xx、超时、连接错误做失败计数；对 2xx 做成功恢复。
   - 在熔断打开状态直接返回降级响应，不再透传到下游。

3. 降级响应规范（草案）
   - HTTP 状态：`503`
   - JSON 字段：
     - `code`: `GATEWAY_DEGRADED`
     - `message`: `服务繁忙，已进入降级保护，请稍后重试`
     - `request_id`: 请求标识
     - `degrade_reason`: 触发原因（timeout/error_rate/open_circuit）
     - `retry_after`: 建议重试秒数

4. 配置项（已新增）
   - `CB_ENABLED`：是否启用熔断。
   - `CB_MAX_REQUESTS`：半开最大探测请求数。
   - `CB_INTERVAL`：统计窗口。
   - `CB_TIMEOUT`：熔断后进入半开前等待时长。
   - `CB_ERROR_RATE_THRESHOLD`：错误率阈值。

### 5.3 开发任务拆分

1. P2-1：断路器基础接入（状态机 + 配置 + 默认值）已完成。
2. P2-2：降级响应结构化与请求追踪字段补齐已完成。
3. P2-3：故障注入与自动化回归脚本已完成。
4. P2-4：联调文档与 README 回归链路升级已完成。

### 5.4 验收标准

1. 熔断状态迁移可观测（closed -> open -> half-open -> closed）。
2. 熔断打开后，响应可稳定返回统一降级 JSON。
3. 故障恢复后，半开探测可恢复正常流量。
4. `go test ./...`、`go build ./...`、`go vet ./...` 通过。
5. 与 `new_idea/run.py` 联调时可稳定复现异常与恢复场景。

## 六、风险与规避

1. 风险：`agent.py` 驱动路径与操作系统不一致导致无法启动。
   - 规避：联调前先完成浏览器驱动自检，必要时调整本机驱动路径配置。

2. 风险：熔断阈值过于激进，导致误熔断。
   - 规避：先在灰度阈值运行，记录真实错误率后再收敛参数。

3. 风险：降级响应与现有调用方约定不一致。
   - 规避：先发布响应草案并与前端/调用方确认字段协议。
